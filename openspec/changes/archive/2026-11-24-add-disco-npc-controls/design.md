# Design

## Context

当前 `DiscoManager` 只在真实直播事件进入 `App.on_event` 时创建或更新角色，内部角色表直接以平台和用户标识拼接出的 key 为键；控制台没有操作运行期角色的 API。前端名称当前固定在角色上方，气泡位置也是近似固定值。相关行为见 `proposal.md` 和 `specs/disco-event-stream/spec.md`、`specs/disco-scene/spec.md`。

## Goals / Non-Goals

**Goals:**

- 在「Disco 舞台」的「角色与舞池」卡片提供运行期 NPC 增删和指定 UID 气泡。
- 让真实用户和手动 NPC 使用不会冲突的内部身份。
- 保持运营操作与直播事件、AI、TTS 完全隔离。
- 让名称固定在图片下方、气泡固定在图片上方。

**Non-Goals:**

- 不把 NPC 或手动气泡持久化到 `config.json`。
- 不让手动 NPC 接收或模拟真实弹幕。
- 不增加 NPC 寻路、自动行为、皮肤编辑或数量上限覆盖。
- 不改变现有真实弹幕创建角色、AI、TTS 和礼物处理逻辑。

## Decisions

### 1. 使用独立身份命名空间

所有真实角色 key 统一增加来源前缀：

```text
有 UID：viewer:<platform>:<uid>
无 UID：viewer:<platform>:name:<hash>
手动 NPC：npc:runtime:<index>
```

角色显示名称与 key 分离，因此真实用户 `npc10` 和手动 NPC `npc10` 可以同时存在。真实弹幕、移动和删除始终按真实角色 key 查询，不会命中手动 NPC。

`DiscoCharacter` 增加 `roleType`，值为 `viewer` 或 `npc`。快照和增量消息携带该字段，前端旧快照缺少该字段时默认为 `viewer`。这种来源字段比通过名称或 UID 文本猜测更可靠。

### 2. NPC 索引在进程内单调递增

`DiscoManager` 持有 `npc_serial`，初始值为 0。只有成功创建 NPC 时递增并生成：

```text
uid = npc:runtime:<serial>
name = npc<serial>
kind = npc
```

删除 NPC 不回收索引；Disco 暂停和再次启动也不重置索引。整个程序重启后从 `npc1` 重新开始。服务未运行、角色已达上限或舞区配置无效时不递增索引。

### 3. 手动 NPC 使用现有角色状态和广播

新增 NPC 使用与真实角色相同的舞区随机位置、皮肤选择、缩放、亮度、层级和 WebSocket 创建消息。NPC 计入 `max_characters`，但不进入真实事件身份映射。超时清理跳过 `kind=npc` 的角色；暂停、重启或关闭 Disco 时沿用现有角色清空流程。

控制台只显示手动 NPC 数量，并通过内部 UID 删除当前索引最大的 NPC，避免列表撑高页面。服务端拒绝删除真人角色，避免运营控件误删观众。

### 4. 运营 API 直接调用 DiscoManager

新增本地 API：

```text
GET  /api/disco/npcs
POST /api/disco/npcs/add
POST /api/disco/npcs/delete   { uid }
POST /api/disco/bubble        { uid, text }
```

这些路由只调用 `DiscoManager` 的管理方法，并通过现有 `_publish` 广播 `create`、`despawn` 或 `say`。它们不调用 `App.on_event`、`Pipeline.on_event`、AI 或 TTS，因此不会形成观众事件。

接口继续使用现有 localhost 和 `X-BVB` POST 守卫。错误响应使用可读中文：服务未运行、达到角色上限、角色不存在、气泡内容为空。

### 5. UID 解析支持原始用户 UID 和内部 UID

发送气泡时先按完整内部 UID 精确查找，允许直接输入 `npc:runtime:3` 或 `viewer:bilibili:123`。若没有精确命中，则按当前直播平台解释为原始用户 UID：

```text
输入 123
当前平台 bilibili
解析为 viewer:bilibili:123
```

目标不存在时返回 HTTP 404 语义和“角色不存在”，不触发创建。成功时复用现有 `_say` 截断、TTL 和 `say` 广播，只更新目标角色。

### 6. 名称和气泡按图片实际高度定位

每个角色视图记录当前图片的显示高度。名称改为顶部锚点并放在脚底下方的固定间距；气泡底部锚定在图片顶部上方。角色换肤后重新计算图片高度，气泡位置随之更新。气泡继续使用真实图片高度而不是角色名称位置，避免大图、小图或 GIF/PNG 换肤后压住图片。

### 7. 皮肤基础缩放叠加在自适应尺寸上

`SkinSpec` 增加 `scale`，默认值为 1。加载皮肤时先保留现有的宽高适配，再把适配后的 sprite scale 乘以该皮肤的基础倍率。这样不同原始分辨率仍使用同一安全显示框，同时运营者可以针对宽高比悬殊或视觉体积不同的图片单独放大或缩小。

控制台在每张皮肤信息行内增加“基础缩放”数字输入。输入变化经过短暂防抖后自动保存，不要求用户移出输入框；配置变化后使用现有配置热更新和皮肤重载流程更新所有已显示角色，不修改图片宽高比。

## Risks / Trade-offs

- **真实角色 key 前缀变化** → 角色状态只存在进程内，重连使用快照恢复；同步修改所有查找路径并在重启窗口部署。
- **同名真实用户和 NPC 在画面上仍可能难区分** → 内部路由完全隔离，控制台 NPC 列表只展示 `roleType=npc`；后续如需要可增加视觉标签，但不属于本次范围。
- **名称移到脚下后可能与前方角色重叠** → 保留白色文字和深色描边，并按脚底 Y 排序；验收重点检查密集舞区中的可读性。
- **直接气泡不刷新真人活动时间** → 手动气泡是测试/运营消息，不伪造真实观众互动；角色仍按真实事件时间超时。
- **NPC 占用角色上限** → 控制台显示明确上限错误，运营者需先删除角色。
- **不展示 NPC 列表会缺少单条定位** → 删除始终作用于索引最大的 NPC，符合单调递增规则且保持界面紧凑。
- **基础缩放可能让角色超出常用视觉尺寸** → 保留现有自适应安全框，缩放只作为倍率，并在输入控件中限制合理正数范围。

## Migration Plan

1. 后端先增加统一身份前缀、`kind` 字段和管理方法，真实事件链路保持原入口。
2. 增加控制台 API 和页面控件，确认 JSON 响应与现有 `api()` 包装兼容。
3. 前端同步 `kind` 类型，并调整名称/气泡锚点。
4. 验证同名真实用户与 NPC、索引递增、暂停清空、目标不存在和无 AI/TTS 副作用。
5. 该变更不新增持久化配置；回滚代码即可恢复旧行为，不需要迁移 `config.json`。

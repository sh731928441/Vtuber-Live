# 设计

## 背景

功能动机参见 `proposal.md`，行为契约参见 `specs/bilibili-live-follow-back/spec.md`。

当前 B 站链路会接收 `INTERACT_WORD_V2`，在 `blivedm` 中解析 `uid` 和 `msg_type`，并且只把普通关注和互粉映射到共享的 `follow` 事件。`App.on_event` 会把所有事件传给 `Pipeline`，由后者执行语音过滤、冷却和按类型合并。因此，后到的关注者可能在合并后失去各自的发送者事件。

扫码登录和手动粘贴 Cookie 都会写入同一个 `bili_cookie`。`BiliLive` 会创建一个能识别 Cookie 的 `aiohttp.ClientSession`，通过导航接口校验登录状态，并保存连接状态和当前登录 UID。界面配置 POST 路由已经支持嵌套配置更新、立即应用配置，并要求请求携带本地 `X-BVB` 请求头。

## 目标 / 非目标

**目标：**

- 在语音合并之前捕获每一个符合条件的关注信号。
- 使用当前 B 站 Cookie 会话和 CSRF 令牌修改关注关系。
- 将网络请求、幂等处理、限速和错误处理与直播 WebSocket 接收循环及语音管线隔离。
- 保持功能默认关闭，并让所有处理结果显示在现有本地日志中。

**非目标：**

- 为抖音增加对应的自动回关功能。
- 在应用重启后持久保存回关历史。
- 自动取关用户、处理特别关注关系变化，或提供关注关系管理页面。
- 绕过 B 站认证、频率限制或风控措施。
- 改变现有关注事件的语音感谢行为。

## 技术决策

### 保留独立的原始关注信号

除现有通用事件发射器外，`_Handler` 还会接收一个独立的关注回调。当 `msg_type` 为 `2`、`4` 或 `5` 时调用该回调，同时保持现有 `emit` 映射不变。这样，特别关注（`4`）可以供新功能使用，又不会开始生成新的感谢语音，从而不改变现有行为。

曾考虑的替代方案：把所有类似关注的事件都加入共享管线，并在管线中读取发送者 UID。该方案被否决，因为关注事件会在配置的窗口期后合并，而合并后的事件不会保留每个发送者的 UID。

曾考虑的替代方案：仅为特别关注额外发出一个合成的 `follow` 事件。该方案被否决，因为这样会产生行为依赖隐藏标志的歧义事件。

### 使用独立的异步回关协调器

在 `bili.py` 中新增 `BiliFollowBack` 协调器，由它持有 `asyncio.Queue`、工作协程以及内存中的 `pending`、`attempted` 和 `seen_mutual` UID 集合。它通过回调取得当前会话、配置、登录 UID、忽略名单和日志上报能力，因此无需构造完整的桌面应用即可进行单元测试。

协调器随应用启动，在设置关闭时保持空闲，并在应用关闭、退出登录、连接断开、登录失效或功能关闭时停止或清空。入队操作只记录任务，所有网络请求都在工作协程中执行，因此同步直播消息回调不会因 HTTP 请求而阻塞。

曾考虑的替代方案：直接在 WebSocket 处理器中调用关注关系接口。该方案被否决，因为它会阻塞消息处理，并使限速和关闭行为难以推理。

### 复用当前 B 站客户端会话

直播客户端初始化后，协调器会使用 `BiliLive.session`。该会话已经包含 B 站域名下的 Cookie，并会在 WebSocket 初始化期间取得 `buvid3`。每次尝试前，协调器都会确认会话仍处于打开状态、`bili_jct` 存在，并且 `BiliLive.login_uid` 表示有效登录。

曾考虑的替代方案：根据 Cookie 字符串另建一个 HTTP 会话。该方案被否决，因为它会遗漏 `buvid3` 等运行时 Cookie、重复维护认证状态，并增加第二套会话生命周期。

### 通过小型适配器提交关注关系修改

适配器会向 `POST https://api.bilibili.com/x/relation/modify` 提交表单数据：`fid` 为关注者 UID，`act=1`，`re_src=11`，`csrf` 为当前 `bili_jct`。请求还会携带直播间 `Referer` 和配置的 User-Agent。JSON 响应中 `code=0` 表示成功，其他状态码会连同安全的 `code` 和 `message` 字段一起上报。

已通过实际网页行为确认动作值映射：`act=1` 表示关注，`act=2` 表示取消关注，`act=5` 表示拉黑。适配器必须对 `act` 使用固定常量并增加单元测试断言，`act=5` 绝不能进入自动回关请求。

网络错误和临时 HTTP 5xx 响应最多重试一次。认证失败、CSRF 校验失败、HTTP 412、B 站风控及其他接口语义错误不会重试。Cookie 值和完整 Cookie 请求头永远不会写入日志。

### 采用保守限速与去重

符合处理条件的关注者采用内存首次出现规则：每个大于零的 UID 在单次应用运行中最多处理一次。请求串行执行，并在请求之间等待 3 至 8 秒的随机时长；第一次请求前也会等待，以避免连接成功后立即形成突发请求。

现有忽略名单会按原始名称或 UID 进行匹配。无效 UID 和当前登录 UID 会被跳过。互粉事件会被标记为已处理并记录为已经互粉，而不会发送请求。这样无需为每个关注者额外查询关注关系，也能提供有效保护。

### 增加一个显式启用的配置节

默认配置新增：

```json
{
  "bili_follow_back": {
    "enabled": false
  }
}
```

B 站账号卡片新增一个复选框，通过现有配置表单绑定。无需新增 HTTP 路由。关闭功能会立即清空等待任务；启用功能会对后续事件生效，无需重新连接。

## 风险与权衡

- **该接口属于非公开网页 API** -> 保持功能显式启用、采用保守限速、公开失败结果，并说明 B 站可能修改或限制该接口。
- **批量回关可能被视为自动化互动** -> 不重试风控响应、串行发送请求，并且绝不向操作者隐藏失败。
- **错误的动作值可能建立拉黑关系而不只是导致请求失败** -> 将关注动作固定为 `act=1`，在请求适配器测试中明确断言 `act != 5`，并在人工验证前关闭功能。
- **等待任务期间当前会话可能关闭** -> 在连接断开时丢弃等待任务，并在工作协程中捕获会话关闭错误。
- **诊断日志可能泄露 Cookie 机密** -> 只记录所需 Cookie 键是否存在，绝不输出 Cookie 内容、CSRF 值或请求头。
- **内存去重无法跨应用重启保留** -> 接受这一初始权衡；直播事件通常不会在重启后重放，持久化历史还会扩大存储和隐私范围。
- **特殊重试时平台响应可能不是幂等的** -> 只在没有收到成功修改响应的传输失败和临时服务端失败时重试。

## 迁移方案

配置合并会为现有安装补充 `bili_follow_back.enabled=false`，因此部署后不会自动启用任何网络行为。回滚时可以关闭该设置或移除协调器，无需修改 Cookie 存储、直播事件历史或现有回复管线。无需迁移持久化数据。

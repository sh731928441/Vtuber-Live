# bilibili-live-follow-back Specification

## Purpose
让 Vtuber-Live 可以使用当前登录的 B 站账号，在直播间出现新的关注行为后按保守规则自动回关，并向主播清楚反馈每个关注者的处理结果。

## Requirements

### Requirement: 自动回关采用显式启用

系统 SHALL（必须）提供一个 B 站自动回关设置，并默认关闭；当设置关闭时，系统不得发送任何关注请求。

#### Scenario: 功能默认关闭

- **WHEN** 用户首次安装程序，或加载的配置中没有自动回关设置
- **THEN** 该设置处于关闭状态，新收到的关注事件不得触发关注关系修改请求

#### Scenario: 用户启用自动回关

- **WHEN** 用户在有效 B 站登录状态下启用自动回关
- **THEN** 后续符合条件的关注事件会进入处理队列，且不需要重启程序

#### Scenario: 用户在有等待任务时关闭自动回关

- **WHEN** 用户关闭自动回关时仍有等待中的请求
- **THEN** 系统丢弃这些等待任务，并且不再发起新的请求

### Requirement: 区分不同类型的关注互动

系统 SHALL（必须）将普通关注（`msg_type=2`）和特别关注（`msg_type=4`）视为可触发回关的事件，将互粉（`msg_type=5`）视为已存在关注关系，并且不得因其他互动类型修改关注关系。

#### Scenario: 普通关注触发回关

- **WHEN** 有效的直播间事件包含 `msg_type=2` 和大于零的关注者 UID
- **THEN** 该关注者可以进入一次自动回关请求的处理流程

#### Scenario: 特别关注触发回关

- **WHEN** 有效的直播间事件包含 `msg_type=4` 和大于零的关注者 UID
- **THEN** 该关注者可以进入一次自动回关请求的处理流程

#### Scenario: 互粉事件被跳过

- **WHEN** 直播间事件包含 `msg_type=5`
- **THEN** 系统记录双方已经互粉，并且不发送关注关系修改请求

#### Scenario: 非关注互动被忽略

- **WHEN** 互动事件不是普通关注、特别关注或互粉
- **THEN** 该事件不会进入自动回关队列

### Requirement: 回关使用当前 B 站登录账号

系统 SHALL（必须）使用通过 B 站扫码登录或手动粘贴 Cookie 提供的登录状态，并且必须同时具备 `SESSDATA` 与 `bili_jct` 才能修改关注关系。

#### Scenario: 当前登录状态可用

- **WHEN** 配置的 Cookie 同时包含 `SESSDATA` 和 `bili_jct`，且 B 站确认账号已登录
- **THEN** 系统可以使用该账号处理符合条件的回关请求

#### Scenario: 缺少 CSRF 令牌

- **WHEN** 配置的 Cookie 缺少 `bili_jct`
- **THEN** 系统不发送关注请求，并提示用户重新登录并提供完整 Cookie 后才能使用写操作

#### Scenario: 登录状态失效

- **WHEN** B 站拒绝当前 Cookie，或返回账号未登录
- **THEN** 系统停止该连接上的回关处理、清空等待任务，并提示用户重新登录

### Requirement: 关注关系修改必须使用关注动作

系统 SHALL（必须）在自动回关请求中发送 `act=1`，并且绝对不得发送 `act=5`。在 B 站网页关注关系接口中，`act=1` 表示关注、`act=2` 表示取消关注、`act=5` 表示拉黑。

#### Scenario: 自动回关使用关注动作

- **WHEN** 系统对符合条件的目标发起关注关系修改
- **THEN** 请求中的 `act` 必须精确等于字符串 `1`

#### Scenario: 禁止发送拉黑动作

- **WHEN** 系统构造任何自动回关请求
- **THEN** `act` 不得为 `5`，并且请求参数校验或测试必须阻止该值进入网络请求

### Requirement: 回关处理相互隔离且不会重复执行

系统 SHALL（必须）将回关任务与 AI 回复生成相互隔离，并对目标去重，确保同一个账号在单次程序运行期间不会收到多次关注请求。

#### Scenario: 合并窗口内出现多个关注者

- **WHEN** 多个符合条件的关注事件在现有关注语音合并窗口内到达
- **THEN** 即使语音管线合并了显示名称，回关处理器仍必须取得每个关注者的 UID

#### Scenario: 同一个关注者重复出现

- **WHEN** 同一个关注者 UID 在程序运行期间被多次加入队列或尝试处理
- **THEN** 系统只处理第一次出现的事件

#### Scenario: 关注请求受到限速

- **WHEN** 多个符合条件的关注者正在等待处理
- **THEN** 系统串行发送关注关系请求，并在请求之间等待 3 至 8 秒的随机时长

#### Scenario: 关注者被排除

- **WHEN** 关注者 UID 无效、与当前登录 UID 相同，或命中配置的忽略名单
- **THEN** 系统跳过该请求并报告跳过原因

### Requirement: 回关结果清晰可见

系统 SHALL（必须）通过现有本地事件日志报告成功、等待中、已经互粉、已跳过、认证失败和平台拒绝等结果，并且不得将这些结果加入 AI 语音回复队列。

#### Scenario: 回关成功

- **WHEN** 关注关系接口对某个关注者返回成功
- **THEN** 系统记录已回关该关注者，并且不为该结果创建 AI 语音任务

#### Scenario: 平台拒绝请求

- **WHEN** 关注关系接口返回非成功状态码
- **THEN** 系统记录关注者、响应码和不含敏感信息的消息，并且不会反复重试认证失败、CSRF 校验失败或风控拒绝

#### Scenario: 发生传输故障

- **WHEN** 请求因网络错误或临时 HTTP 服务端错误而失败
- **THEN** 系统可以在不阻塞直播事件处理的情况下重试一次，并在重试仍失败时记录最终结果

### Requirement: 兼容现有直播回复

系统 SHALL（必须）在新增自动回关能力的同时保留现有关注感谢、语音合并、冷却、队列优先级和 AI 回复行为。

#### Scenario: 启用自动回关

- **WHEN** 普通关注或互粉事件同时符合现有关注感谢的语音回复条件
- **THEN** 原有语音行为保持不变，回关处理器独立运行
